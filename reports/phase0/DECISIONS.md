# Phase 0 决策记录

审计日期：2026-08-28

## D-001：仓库内部关键点名称

- **问题**：使用 `PS1/PS2/FH1`，还是立即改名为 `PS_R/PS_L/FH_T`？
- **可选方案**：保留原始字段名；全仓重命名；在入口建立别名。
- **采用方案**：模型通道与结果固定为 `PS1/PS2/FH1`，顺序为 `(PS1,PS2,FH1)`；别名只用于文档解释。
- **理由**：原始 CSV 和官方监督代码直接使用这三个字段，可减少静默换序风险。
- **证据来源**：公开 CSV 字段、官方 IUGC 代码和 901 条标签的 x 顺序统计。
- **需要导师确认**：否；若论文最终要求使用另一套术语，只调整展示名称，不调整通道顺序。

## D-002：PS_R / PS_L / FH_T 对应

- **问题**：三组术语如何对应？
- **可选方案**：不绑定；依据图像左右位置绑定；由经验猜测。
- **采用方案**：解释性映射采用 `PS1=PS_R`、`PS2=PS_L`、`FH1=FH_T`。
- **理由**：官方论文称 PS1 为 rightmost point、FH1 为 tangent point，且 901/901 条记录满足 `PS1.x>PS2.x`。
- **证据来源**：官方 baseline 论文、公开标签聚合统计。
- **需要导师确认**：否，但代码仍保留原始名称。

## D-003：坐标顺序和归一化

- **问题**：坐标是 `[x,y]` 还是 `[y,x]`，DSNT 应使用哪种网格？
- **可选方案**：两种顺序；`align_corners=True/False`。
- **采用方案**：点使用 `[x,y]`，尺寸使用 `[H,W]`，数组访问为 `image[y,x]`，全链路 `align_corners=True`。
- **理由**：与官方读取代码、现有转换函数、DSNT 和单元测试一致；256 宽度下归一化 0 对应 127.5。
- **证据来源**：官方 IUGC 数据代码、`coordinates.py`、`dsnt.py`、坐标测试。
- **需要导师确认**：否。

## D-004：AoP 定义

- **问题**：顶点、射线顺序、有向角和补角如何处理？
- **可选方案**：PS1 或 PS2 为顶点；无向角或有向角；原角或补角。
- **采用方案**：`AoP=∠PS2–PS1–FH1`，PS1 为顶点，使用 `[0°,180°]` 无向角，不取补角。
- **理由**：逐行重算 901 条标签，最大差小于 `5×10^-8°`；其他顶点不能复现标签。
- **证据来源**：公开标签的几何重算、官方 baseline 定义。
- **需要导师确认**：否。

## D-005：水平翻转

- **问题**：是否把水平翻转加入训练增强？
- **可选方案**：直接翻图；翻图并交换 PS1/PS2；禁用。
- **采用方案**：Phase 0 配置禁用水平翻转。
- **理由**：PS1/PS2 具有图像右/左端点语义，只翻图会破坏通道定义。虽然已有交换函数和测试，正式数据增强链路尚未完成联合验证。
- **证据来源**：坐标契约、`horizontal_flip_points` 单元测试。
- **需要导师确认**：否；后续启用前需新增端到端增强测试。

## D-006：图像通道和解码

- **问题**：输入按 RGB 还是灰度读取，是否依赖 `.jpg` 后缀？
- **可选方案**：保留三通道；转换单通道；按扩展名选择解码器。
- **采用方案**：用 Pillow 按文件内容解码并显式 `convert("L")`，模型输入单通道。
- **理由**：901 张图以 RGB 存储但三个通道完全相同；另有 188 个 PNG 内容使用 `.jpg` 后缀。
- **证据来源**：全量图像格式和通道审计。
- **需要导师确认**：否。

## D-007：数据划分

- **问题**：是否重新随机拆分 300 张标签数据？
- **可选方案**：单图随机拆分；使用官方 train/validation；等待分组信息后重做内部验证。
- **采用方案**：Phase 0 使用官方 train 300 和 validation 100，不再进行单图随机划分。
- **理由**：官方 validation 已存在；同时缺少患者/视频字段，随机拆分可能造成近邻帧泄漏。
- **证据来源**：公开目录、字段审计、跨 split 相邻编号候选。
- **需要导师确认**：若后续需要论文内部交叉验证，则需要确认分组元数据或认可其局限。

## D-008：Testing 使用边界

- **问题**：是否在开发过程中反复查看 testing 指标？
- **可选方案**：每轮评估；用于调参；冻结方案后一次评估。
- **采用方案**：只在 validation 选模型和训练轮数，方案冻结后再进行一次 testing 评估。
- **理由**：避免测试集参与调参；testing 还存在内部重复和标签差异。
- **证据来源**：标准实验协议、重复审计。
- **需要导师确认**：否。

## D-009：完全重复记录

- **问题**：testing 内重复记录是否删除？
- **可选方案**：删除；只按唯一内容统计；保留官方行级口径并补充唯一内容统计。
- **采用方案**：不修改官方数据，主 benchmark 按 501 行报告，同时注明只有 493 种唯一内容；可附加去重复敏感性分析。
- **理由**：保持与官方评价口径一致，又不隐瞒重复加权和同图标注差异。
- **证据来源**：文件与像素 SHA-256 审计。
- **需要导师确认**：论文最终表格是否增加去重敏感性结果需要确认。

## D-010：无标签训练启动条件

- **问题**：是否先用少量样例实现完整半监督链路？
- **可选方案**：用孤立样例占位；生成伪数据冒充；等待完整数据；先用合成数据做模块测试。
- **采用方案**：真实半监督训练等待完整无标签池；当前只允许合成测试和监督 Phase 0。
- **理由**：本地可用无标签池为 0，少量审计样例不能代表完整公开数据；当前 Kaggle v1 包结构预期 31,421 张，而其他材料的 31,121 口径仍待确认。
- **证据来源**：文件系统和压缩包完整性审计。
- **需要导师确认**：需要确认完整数据获取方式、存储位置和访问权限。

## D-012：DSNT 监督路径

- **问题**：0--1 Gaussian 热图 MSE 与 spatial-softmax DSNT 能否直接共用同一输出？
- **可选方案**：只做热图 MSE；只做坐标损失；联合 MSE、坐标损失和概率分布约束。
- **采用方案**：`MSE(raw_heatmap, Gaussian) + 10×SmoothL1(DSNT coordinate) + JS(probability, normalized Gaussian)`。
- **理由**：256×256 网格上，峰值仅为 1 的理想 Gaussian 经普通 softmax 后仍几乎均匀；tiny 诊断中加入 JS 后，MRE_ALL 从 121.699 px 降至 1.049 px，概率图也恢复为局部峰值。
- **证据来源**：DSNT 原论文的坐标监督与分布正则思路、`test_dsnt.py`、真实 4 样本 tiny-overfit。
- **需要导师确认**：否；后续消融仍应分别报告三个损失项的作用。
